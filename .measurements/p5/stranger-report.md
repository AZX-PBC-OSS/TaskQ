## (b) The workflow API (docs-only explanation)

**Declaring a flow with a map and a join.** You opt in with the `taskq[flows]` extra and `import taskq.workflows` (the "import law": plain `import taskq` never loads it). Step bodies are typed async functions decorated with `@app.actor(queue=...)` on a `WorkflowApp`; the flow itself is a `@app.workflow("name")` function that is **sync and pure** — it spells the graph by dataflow and is compiled fresh each time. The wiring verbs are `step`, `gather`, `map_source`, `sink`, `build`. `step(body, *args, key=...)` returns a `Promise[R]`; when one call receives **several promises**, that call becomes the fan-in **join**, and its body *is* the join's reducer, receiving the parents' decoded results (e.g. `reduce(ctx, a: Stats, b: Stats) -> Stats`). `gather([...])` is the all-upstream join, yielding a flat `Promise[list[A]]`. The **map** is `map_source(source, item_body)`: the source's body returns a list, the engine forks one fresh job per item at the source's finalize, the join collects their results, and downstream sees the flat `Promise[list[R]]`. Every join declares a failure policy via `on_failure=` — default `"fail_closed"` (a terminally failed parent blocks the join, peer-cancels running peers, fails the run) versus an absorbing policy where failures fan in as typed `FailureInfo` items and the join fires with partials. `build(result, *residuals)` is the completeness point; `compiled.validate()` runs the E1–E7/W1 rule matrix before any row is written. To execute: `FlowRunner(compiled, pool, schema).create_flow(input=..., run_key=...)`, then `drive(flow_id, until="held" | "terminal")` — or let fleet workers execute the rows through their normal queues; `result(flow_id)` reads the decoded answer.

**Resolving a human-approval hold.** A body suspends with `decision = await ctx.wait_signal((ReviewDecision,), timeout_s=..., reason=...)` — the typed wait registers a **hold row** and the node parks (amber in the admin's run explorer). The operator finds it with `taskq flows holds <run_id>` or the admin run page's "Holds & decisions" panel, then answers with `taskq flows resolve <hold_id> '<json>' --app myapp.workflows:app` — the payload is validated against the declared pydantic models before anything moves; a wrong shape is refused (exit 1, named pydantic error) and the hold **survives** — or programmatically via `HitlClient(pool, schema).list(flow_id)` / `.resolve(hold_id, {...})`. Resolve is idempotent and audited. On delivery the body re-executes **from the top**; the delivered answers are consumed per hold epoch and read with `ctx.signal(name)`; a resume consumes **no** retry-ladder attempts (resume-not-retry). An expired hold is marked `abandoned` and the wait site raises `SignalTimeoutError`, which the body's own ladder owns.

## (c) Every stumble, numbered

1. **The flagship demo is undiscoverable from the front doors.** The root `README.md`, `docs/index.md`, and `docs/getting-started/quick-start.md` never mention it. The only docs pointer is buried at ~line 1249 of `docs/guides/actors.md`. Without the assignment's hint I would likely never have found `examples/fleet_demo/`.
2. **The flagship demo never demonstrates the workflow engine.** Seven acts cover actors, rate limits, cancel, cron, SIGTERM, doctor, insights — and zero workflows, despite workflows being the docs' largest subsystem. The only workflow walkthrough is `docs/examples/doc-ingest.md` (CI-fenced code, not a runnable-by-me demo) and the admin run explorer.
3. **The join failure policy has two different names in the docs.** `docs/guides/workflows.md` (§3/T06) says `on_failure="fail_closed" | "collect"`; the runnable example in `doc-ingest.md` uses `on_failure="maybe"`; the API reference's verb table never names the non-default value at all. I could not tell which string is real, and I was not allowed to read the source to check.
4. **A mid-run death leaves the demo's containers behind with no newbie-visible recovery path.** Run 1 died after Act 4; the `down -v` only runs in the final act. The README's prose does name the compose project, so I could reconstruct `docker compose -p taskq-fleet-demo down -v`, but nothing tells you to check or clean up after a failed run.
5. **Act 4's headline promise is flaky.** The README says "Watch the `cron-fire-budget-deferred` events." Run 1: 11. Run 2: **0**. A newcomer re-running the demo sees the README's promised behavior silently missing, with no explanation in the docs.
6. **Cosmetic output bug in Act 4:** `digest 'cron fired' events during the crawl: 7` followed by 6 listed lines.
7. **The workflows guide is inside-out for a newcomer.** The first ~400 lines of `docs/guides/workflows.md` are engine internals (two-transaction finalize, fencing tokens, ledger arbiters, a measurement-curve refit debate) before §1 "The flow API: the concept" teaches you how to declare anything. The friendly "thirty-second tour" lives in the *API reference*, not the guide. Section numbers are jumbled: §1, §2, §3, §9, §10, §4, §5, then unnumbered pages, then §7 — no §6, no §8.
8. **The guide's core arguments cite artifacts outside the docs** — `.measurements/t17-dispositions.md`, `.measurements/t10-hold-resume-band.json`, `perf-evidence-*.md` — repeatedly and as load-bearing evidence. A docs-only reader (or anyone without the repo's measurement tier) cannot verify any of it.
9. **The official example imports a private module:** `doc-ingest.md` does `from taskq.workflows.api._hitl import HitlClient`. An underscore path in the docs, with no public re-export documented anywhere I read. Where am I *supposed* to import `HitlClient` from?
10. **Broken link in `doc-ingest.md`:** "the demo app" points at `https://github.com/#/examples` — a placeholder that goes nowhere — and "see the demo's README" names no path.
11. **The `taskq flows` verbs are missing from the CLI API reference.** `docs/api-reference/cli.md` has zero mention of them; they're only in `docs/guides/cli.md` §`taskq flows`. Worse, the workflows guide's own diagnosis runbook (§7) tells me to run `taskq flows status/holds/retry` but never mentions `taskq flows resolve` — the one verb the HITL story needs. I found the resolve command only by grepping.
12. **Two competing "run a flow" surfaces.** The guide mentions `workflows.run(flow, input, key=…)` exactly once, never again and with no signature; the API reference documents only `FlowRunner.create_flow`. I guessed they're the same machinery; the docs never say.
13. **"Fleet" means three things.** The docs use "the fleet" for the worker fleet generally; the demo is the "fleet demo"; and the demo's own queue name is literally `fleet` (`TASKQ_QUEUES=fleet`). Three overlapping meanings in one feature.
14. **The README's quick start and the demo's path are never reconciled.** The root README makes you do `docker compose up -d postgres redis`, `cp .env.example .env`, `uv sync`, migrations — the demo needs none of that (it manages its own stack on shifted ports). Nothing says the quick-start steps aren't prerequisites for the demo. (They aren't.)
15. **`migrations applied: 0` in Act 0 looks like a failure** on a re-run. It means "already applied"; nothing in the demo output or README says so.
16. **An undecodable jargon wall.** The workflows docs speak in insider shorthand — "the dragon", "D1's BODY-FROM-DEFINITION discipline", "P3 rule 7", "cut #4", "round-8", "T06/T07/T09/T10/T17", "the convicted variant" — with no glossary and no table decoding the T-numbers. Much of the guide is unreadable without context I was told not to acquire.
17. **Documented-but-never-demonstrated parameters.** `ctx.wait_signal(..., tool=…, args=…)` appears in the guide's signature; every example passes only `reason=` (and `timeout_s=`). Likewise `GateDecl` shows three fields in the example and nowhere else is its contract spelled out.
18. **A parameter-ordering sentence I had to read five times** (guide §9): "DECLARATION ORDER DECIDES NOTHING in the payload door — by shape." I *still* cannot paraphrase with confidence what the payload door does with declaration order. The docs assert the conclusion without stating the rule.

**Summary verdict:** the demo works end to end (run 2: every act, clean cleanup, zero errors), and the workflow API *is* explainable from the docs — but only after assembling it from three separate pages (guide §1/§3/§4, API reference, `doc-ingest.md`), and two of those pages disagree on a keyword. The stumbles are concentrated where a newcomer lives: discoverability, the first 400 lines of the workflows guide, and the docs' habit of arguing with themselves in citations a stranger can't open.
